# SGMA local persistent application
Status: proposed local-only application increment. Container-ready packaging, not authorized for online deployment. No authenticated users or RBAC; use only synthetic data. Existing stateless workbench remains available.
## Windows setup (Command Prompt, non-admin)
1. Stop the old workbench with Ctrl+C. From the repository root pull the integrated branch **after merge**. Create a virtual environment: `py -m venv .venv-sgma`; activate: `.venv-sgma\Scripts\activate.bat`; install: `python -m pip install -r Enterprise-Security-Automation\sgma\requirements.txt`.
2. In MySQL Workbench connect to the local server and run `SELECT VERSION();`. MySQL 8.0.18+ required for the bootstrap script. Run sgma/bootstrap.sql as administrator. It creates a fresh dedicated schema and application account, not other databases. If account already exists, stop and review rather than recreate. Save the generated password privately; do not screenshot or paste it into chat.
3. In Command Prompt temporarily set `set SGMA_DB_USER=root` (or your schema administrator account) and run `python Enterprise-Security-Automation\sgma\app.py init-db`. Enter admin password at hidden prompt. This creates schema v1 tables via SQLAlchemy metadata, does not perform future migrations. Then `set SGMA_DB_USER=sgma_app` and run `python Enterprise-Security-Automation\sgma\app.py serve`; supply generated app password at hidden prompt. Do not set a persistent password environment variable. Browse http://127.0.0.1:8765. Verify /health.
4. Import your existing proposal/evidence JSON, select scanners confirmed completed, evaluate and save. Change revision for changed profile content. Reload saved history after restart to prove persistence. Workbench can inspect projects, profile_revisions, assessments and audit_events with SELECT only.
## Configuration and deployment boundary
Default localhost MySQL port 3306, database sgma, runtime user sgma_app. Override using SGMA_DB_HOST, SGMA_DB_PORT, SGMA_DB_NAME, SGMA_DB_USER, SGMA_DB_PASSWORD (runtime secret injection only), SGMA_DB_TLS_CA for nonlocal DB. SGMA_MODE must be local. No cloud credentials or provisioning. Dockerfile build context is Enterprise-Security-Automation; container uses nonroot runtime. Publish only on 127.0.0.1:8765, never all interfaces; container DB connectivity requires additional network/TLS configuration and is not validated. Image base is tag-pinned, not digest-pinned; full dependency lock, authenticated deployment, RBAC, CSRF review, reverse proxy TLS, migration tooling, backups, managed secrets and private DB network must precede any online deployment. No public access through GitHub Pages.
## Data integrity
Projects -> versioned profile snapshots -> assessments -> audit events. Unique project/revision prevents silent overwrites; app account has SELECT/INSERT only. Canonical JSON hashes support corruption checks, not authentication or tamper-proof storage. Imported evidence remains user-declared/unverified; approval and compliance flags remain false. No actual policy enforcement changes. Runtime baseline is pinned to repository sample; required manual baseline row protected. Audit actor explicitly unverified. No deletion endpoint. This is an initial schema rather than a fully normalized decision management database.
